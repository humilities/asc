在高性能计算（特别是跑 HPL 和 HPCG 这类基准测试）时，“固定 OpenMP 和 BLAS 线程数”指的是**显式设置并锁定多线程并行计算时的线程数量**，防止它们在后台自动乱开线程导致资源争抢或性能波动。

这两个线程数分别对应不同的计算层级和库：

### 一、 OpenMP 线程数是什么？

- **作用层级**：**循环/代码级多线程并行**。
- **谁在用**：由编译器通过 `#pragma omp parallel for` 等指令控制的并行区域。在你之前跑的 `HPCG` 报告里，开头就有 `Threads per processes=1`，文档中也提到先按 MPI-only（`THREADS=1`）实验，之后再做混合 OpenMP 实验。   
- **常见控制变量**：
  - `OMP_NUM_THREADS`：设置每个进程（MPI rank）可用的 OpenMP 线程数。
  - `OMP_PROC_BIND` / `OMP_PLACES`：控制线程绑定到哪些 CPU 核心，避免线程乱飘。

### 二、 BLAS 线程数是什么？

- **作用层级**：**底层线性代数库的多线程并行**。
- **谁在用**：像 OpenBLAS、Intel MKL、BLIS 这类基础数学库，内部实现矩阵乘法（如 `DGEMM`）时会自动创建多线程加速。在跑 `HPL` 时，最耗时的矩阵分块运算重度依赖 BLAS 库（文档中示例链接的是 `-lopenblas`）。   
- **常见控制变量**：
  - `OPENBLAS_NUM_THREADS`（OpenBLAS 常用）
  - `MKL_NUM_THREADS`（Intel MKL 常用）
  - `OMP_NUM_THREADS`（部分 BLAS 库在未单独指定时也会参考它）

### 三、 为什么要“固定”它们？（尤其是在 MPI + 多线程场景下）

如果你同时使用了 **MPI 进程** 和 **多线程**，不固定线程数很容易出问题：

1. **防止线程超订（Oversubscription）**：假设机器只有 4 个核，你起了 4 个 MPI 进程，而 OpenBLAS 默认每个进程又开 4 个线程，总共就会挤出 16 个线程抢 4 个核。频繁的线程上下文切换会导致性能暴跌甚至卡顿。
2. **保证实验可复现与对比公平**：跑基线或调优对比时，如果线程数随环境或自动策略变化，每次测出来的耗时和 GFLOPS 就没有可比性。
3. **避免多层级线程冲突**：有时 OpenMP 和 BLAS 各自开线程会互相争抢 CPU 资源，通常需要按“总核数 = MPI 进程数 × 每进程线程数”来合理分配（例如单节点纯 MPI 或每进程固定 `1` 线程 / 固定 `N` 线程）。

### 四、 结合你们的测试怎么理解？

- 在你前面的 **HPCG** 结果中，`Distributed Processes=4`、`Threads per processes=1`，说明用了 4 个 MPI 进程，每个进程固定为 **1 个线程**，没有额外开启多线程。
- 在后续做调优或对比实验时，通常会把 `OMP_NUM_THREADS` 和对应的 BLAS 线程变量（如 `OPENBLAS_NUM_THREADS`）明确写进运行脚本里固定下来，这样每次测试的线程配置清晰可控，也方便排查性能变化到底是改参数带来的，还是线程数变了带来的。

在挑选基准测试（尤其是 HPL / HPCG 这类吃内存和带宽的高性能计算负载）的最优配置时，要求“没有 OOM 或 swap”，核心原因在于：**一旦发生 OOM 或 Swap，测试结果就会失真、不可复现，甚至直接中断失败**。

具体来说，可以从以下四个实际层面来理解：

### 一、 OOM（Out Of Memory，内存耗尽）会导致直接崩溃或“静默失败”

- **进程被强杀**：当矩阵规模 `N` 设得过大、分块/缓冲区占满可用内存时，Linux 内核的 OOM Killer 可能会直接杀掉 `xhpl` 或 `xhpcg` 进程，导致测试中断、拿不到有效结果（甚至 `exit_code` 异常）。
- **边界试探危险**：调优时大家常想把矩阵 `N` 尽量开大（因为 HPL 通常 `N` 越大，计算占比越高、Gflops 越好看）。但一旦踩过物理内存红线，不仅当前这轮跑崩，还可能连带影响同节点上的其他进程或系统稳定性。

### 二、 Swap（交换分区）会让性能“虚高或严重暴跌”，失去调优意义

- **磁盘/虚拟内存延迟极高**：Swap 本质上是把内存页换出到磁盘（或虚拟交换空间）。HPL 和 HPCG 都是内存密集型负载，一旦发生频繁换页（thrashing），耗时往往会成倍甚至几十倍拉长，Gflops 断崖式下跌。
- **掩盖真实参数优劣**：假设某组参数其实计算效率很好，但因为 `N` 稍微偏大触发了 Swap，跑出来的 Gflops 却很差，你就会误判这组参数不行；反之，如果某次 Swap 抖动恰好比另一次轻，也会让对比失去意义。
- **违反基准测试的有效性原则**：基准测试衡量的是**计算硬件与内存系统的真实有效算力**，依赖 Swap 换出来的性能不代表机器可持续的正常计算能力。

### 三、 破坏“重复运行结果稳定”

- Swap 的发生往往带有很强的随机性和系统状态依赖（比如当前系统缓存多少、后台有没有抖动、换页何时触发）。
- 即使输入参数完全一样，只要某一次碰巧触发了 Swap 或内存吃紧，耗时和 Gflops 就会大幅波动，导致多次运行结果无法稳定复现。

### 四、 结合你们当前的环境（WSL2 / 服务器）怎么看？

- 在 **WSL2** 环境中，可用内存本身受限于分配给 WSL2 的上限，跑大一点的 `N` 更容易逼近内存边界（文档中也提醒过空闲内存不足时要降低 HPL 的 `N` 或减少 ranks）。   
- 即使后面转到**老师的服务器**，也不能盲目把内存吃干抹净去冲一个极限数字——生产或正式评测中，留出安全余量、保证**零 OOM、零 Swap**，选出来的配置才是稳妥、可复现、真正能落地的配置。
